# Case Study 01｜AI 商品文案自動化：從人工撰稿到批次生成

> **一句話**：把「已取號未上架」商品的 SEO 文案撰寫，從人工逐筆撰稿改為 AI 批次生成並自動回寫兩張表單，累積處理 83 筆商品、11 個批次、100% 寫入成功。

**角色**：需求定義、流程設計、實作、上線後維運（獨立作業）
**期間**：`【待填：起訖月份】`
**技術 Demo**：[product-seo-demo](../product-seo-demo/index.html)

---

## 1. 問題

公司在宜搭（釘釘低程式碼平台）用 J1 表單管理新品開發。商品取號後、正式上架前，需要有人替每一筆商品產出：

- SEO 產品名稱
- 產品描述
- HTML 格式的詳情內容
- 商品標籤

這些內容寫完還要分別回寫進 J1 與 J1A 兩張表單。

**原本的狀態**：這件事一直有人在做，但**沒有系統化**——沒有一套共用的命名規則，全憑寫的人各自判斷。結果就是同一批商品，不同人、不同時間寫出來的風格不一致，SEO 效果無法累積。

`【可補：原本大約幾個人在寫、一筆花多久，讓對比更具體。沒有精確數字就留這句質性描述即可。】`

**所以真正的痛點不是「打字很慢」**，而是**品質不穩定、規則不可累積**。這個判斷決定了我要解的不是速度，是一致性。

## 2. 我的判斷

我把它定義成**內容品質一致性問題**，而不是人力不足問題。所以目標不是「寫得更快」，而是「讓每一筆都遵循同一套可被檢驗的命名規則」。

這個定義決定了後續所有取捨：如果目標只是快，我會直接找現成的 AI 寫作 SaaS；但要規則一致且可調整，就必須自己掌握 prompt 與寫入流程。

## 3. 做法

**架構**：BAT → PowerShell → `claude -p`（headless CLI）→ Node.js 批次鏈

**關鍵決策**：自建零依賴的 `yida-form` skill 直連宜搭 OpenAPI，不透過中間層。商品圖片辨識直接走模型內建 Vision，不另接 OCR 服務。

## 4. 四個關鍵取捨（PM 面試主軸）

| 決策 | 原本做法 | 改成 | 為什麼 |
|---|---|---|---|
| **篩選條件** | 初版條件過寬 | 兩次收緊修正 | 抓進不該處理的商品，成本浪費且污染資料 |
| **B2B 通用詞** | 限量允許 | 全面禁止 | 通用詞讓不同商品的命名趨同，SEO 互相稀釋 |
| **命名策略** | 關鍵字堆疊 | 場景／問題前置 | 堆疊在搜尋引擎已失效，且對真人不可讀 |
| **關鍵字來源** | 外接關鍵字庫 | 從商品原始資料推斷 | 外部庫綁定特定品類，換品類就失效；改為推斷後**跨品類通用** |

最後一項是我最想談的：捨棄外部關鍵字庫**短期會讓文案品質略降**，但換來系統能處理任何新品類而不需重新建庫。這是拿即時效果換長期適用範圍。

## 5. 踩過的坑與修正（這段是重點，別跳過）

**事故：靜默寫入失敗**

宜搭 API 在缺少 `useLatestVersion: true` 參數時，寫入新欄位會**失敗但回傳空物件，不報錯**。同時 HTML 欄位的 key 我從一開始就寫錯，導致**歷史批次的該欄位全部靜默失敗**——直到 2026-06-08 才發現。

**修正**：所有寫入操作一律加上「寫後回讀」驗證，確認寫進去的值與預期相符才算完成。

**我從中學到的**：API 回傳 200 不等於資料寫進去了。任何寫入型整合，驗證步驟必須是讀回實際值，不能信任回傳狀態碼。這條後來成為我所有專案的固定規範。
