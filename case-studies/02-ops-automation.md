# 02｜營運流程自動化

**一句話**：把一間只靠人腦和 Excel、沒有資料系統的傳產轉電商公司，一條一條帶進自動化——一個人從需求盤點、排序、動手實作到跨部門推行全包。

**技術棧**：n8n 流程自動化 · Python 自建串接程式 · Meta／Threads 官方 API · 釘釘宜搭 OpenAPI · QR Code 流程追蹤

**角色**：需求盤點 · 決定先做哪一條 · 流程設計 · 動手實作 · 跨部門推行（全程獨立作業）　**期間**：`【待填】`

### 系統架構

這個案子是三條各自獨立的營運流程，我一條一條數位化：

- **社群數據回寫**：自寫程式串 FB／IG／Threads 三平台官方 API，把三邊格式各異的貼文成效，自動對應進公司內部釘釘宜搭表單、定期刷新回寫。這條有完整程式碼、可實際展示。
- **貨運 QR Code 全流程**：收貨 → 驗貨 → 加工 → 出貨四環節，用掃碼串成一條可追蹤的流程。
- **財務月結重設計**：拆分帳戶功能、做表單連動與異常通知，讓會計月底結帳不用再整天人工比對多張表。

三條共用同一套工具分工原則：需要視覺化、要快速把多個服務串起來觸發的用 n8n；需要穩定、能搬機器、能測試的抽成 Python。常見演進是先用 n8n 做原型快速驗證，跑穩後把核心邏輯改寫成 Python、掛正式排程長期跑。

### 技術重點

- **自建三平台資料串接管線**：自己寫程式直接串 FB（Page feed）、IG（media）、Threads 三個平台的官方資料介面。三邊回傳的欄位結構、命名、資料型別都不一樣，我做了一層自建轉接，把它們統一對應到公司內部宜搭表單該有的欄位，再透過釘釘宜搭 OpenAPI 定期刷新回寫。重點是「一套自建串接層吃多平台、把不同格式統一收斂成公司系統要的單一乾淨樣子」。
- **抓取到寫回是一條完整管線**：從各平台 API 拉貼文（內文、發布時間、連結、互動數、圖片、hashtag），經過轉換層清洗——內文做 HTML escape、換行轉標籤、hashtag 用規則抽取、輪播貼文取代表圖——最後以「認得出同一篇貼文就更新、認不出才新增」的方式寫回宜搭。表單不會愈跑愈肥，數字永遠是最新的。
- **從視覺化流程工具真實遷移到自寫程式**：這條流程原本是用 n8n 在畫布上拉線做的，後來我把整條改寫成 Python 版。動機是 n8n 綁在特定主機上，Python 版可以整包複製、搬到任何機器上獨立排程跑，也能寫測試驗證。兩個版本我都留著可對照——這是我對「同一條流程做過 n8n → Python 完整遷移」最扎實的證據。
- **刻意零第三方依賴、可搬移**：串接程式只用語言內建的網路庫，不裝額外套件，複製到新機器就能直接跑，不用先花時間佈環境。網路連線失敗時內建自動重試，不會一次連不上就整條斷掉。
- **懂平台 API 的邊界**：FB／IG 的互動數是我從官方 API 真的抓回來的，而且會受帳號 token 權限影響能不能拿到；Threads 官方 API 目前不開放對應數值。我能清楚區分「這是平台真給的數據」和「這是平台不開放、只能留位置」，不會把兩者當成同一種可信度混著講。
- **遷移時順手砍掉死流程**：舊 n8n 版裡有一段接到別的購物平台、但其實根本沒真的寫回任何地方的殘留分支。改寫時我把它整段移除，只留下真正有用的三平台回寫。重寫是清理死路徑的好時機。
- **排程知道邊界**：程式雖然內建「自己一直開著跑」的選項，但我在文件裡註明正式環境應交給作業系統的正規排程工具定時觸發——因為一支程式自己長時間開著不關，久了容易出狀況。
- **貨運 QR Code 串起四環節**：收貨、驗貨、加工、出貨原本各自獨立、無串連。我為每環節設計獨立表單（收貨記時間品項、驗貨記規格與工時、預計到貨、出貨記裝箱數與郵寄狀態），用 QR Code 把各環節表單連起來、觸發表單連動與自動通知。業務掃一次碼就能看到該筆貨在各環節的完整資料，狀態也自動帶到下一階段。附帶做了兼職計時與薪資換算的儀表板。
- **財務月結流程重設計**：把原本各自獨立的多個銀行帳戶、收付款、零用金、支出表，重新拆分帳戶功能並做資料連動——會計輸入一筆交易後相關表單自動更新，再加上總表彙整、異常即時通知與多人查改權限。（這條我沒有留下可展示的程式碼，定位為流程與營運面的重設計，不宣稱技術實作深度。）

### 核心設計決策

- **工具分工，不是二選一**：確定性的規則、需要測試把關的邏輯走 Python；需要視覺化編排、把多個服務串起來觸發的走 n8n。兩種各有位置，看任務性質分配，而不是全押一邊。同一條社群流程我就是先用 n8n 出原型驗證，跑穩後把核心邏輯改寫成 Python 上正式排程。
- **為什麼先做貨運和財務**：這兩條都同時命中「一直重複發生 × 規則很明確 × 出錯代價很高」。一直重複，省下來的時間才會複利放大；規則明確，機器才接得住；出錯代價高，自動化就同時是在降風險。
- **排順序本身就是 PM 的工作**：資源就我一個人，決定「先做哪一條、為什麼是這個順序」，比「全都想做」更重要。
- **敘事按證據強弱排**：先講最經得起檢驗、有程式碼可看的社群這條；成果敘事和技術證據我分開講、不混為一談。

### 關鍵數字

- **社群同步**：一套自建串接層自動把三個平台的貼文數據對應進公司表單、定期刷新回寫，同一篇不重複堆疊。✅ 這條有完整程式碼可實際展示。
- **貨運內部確認時間 −50%**：`【待你確認】`（履歷檔曾寫過，但我沒有親自量測、也沒有前後對照數據，所以不逕自寫進成品）
- **財務人工作業量 −50%**：`【待你確認】`（同上，履歷曾寫、未經量測佐證）
- **財務月結 從 1 天縮到 2 小時內**：`【待你確認】`（同上，履歷曾寫、未經量測佐證）
- **每月省下 20+ 小時人工**：`【待你確認】`（履歷曾寫，但沒有拆解各條流程各佔多少，也未經量測佐證）
- **貨運查詢 從數小時 → 即時**：質性描述保留（業務原本被客人問「貨到哪了」答不出、要拜託貨運去查；掃碼後當場就能看到），但不掛具體百分比。

### PM 力展現

- **排序判斷**：面對老闆「什麼都想數位化」，我不照單全收，而是用「重複發生 × 規則明確 × 出錯代價高」三個準則，排出應該先做哪一條。
- **跨部門推行不靠職位壓人**：貨運 QR Code 這條，我先做一個能掃、能看到貨況的小原型，丟給倉庫同事實際試用，好用了再回頭說服比較保守的業務端——由下而上擴散，化解傳產轉電商裡各部門的觀望。
- **從共同痛點切入**：業務痛在被客人問貨況答不出來，倉庫痛在不知道貨到哪一站；我把方案定位成「一次解你們兩邊的痛」，而不是「上面交代的新規定」，大家才願意用。
- **懂平台的邊界**：我能清楚區分「平台真給的數據」和「平台不開放、只能先留空的位置」，不會把兩者混為一談當同一種可信度講。
- **誠實標注數字**：我主動點出一個結構性錯配——最漂亮的商業數字落在沒有程式碼佐證的貨運／財務兩條，而有完整程式碼的社群這條反而沒有響亮數字。這個實話我選擇講出來。
- **不硬湊數字**：貨運／財務的省時數字我沒親自量測、也沒有前後對照，就一律標「待確認」，絕不硬套到有程式碼的那條上去借光。
- **主動揭露待驗證項**：社群這條我自己就標出還沒完全驗證的點（一個新增的備註欄是否真的存在於後台、社群互動數字準不準取決於帳號權限），實際展示前應先回後台確認過。
