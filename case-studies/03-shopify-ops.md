# Case Study 03｜電商營運系統整合：三系統同步、法規合規下架與 AI 協作基礎設施

> **一句話**：為正式營運中的 Shopify 商店建立自建管理 App 與 AI 協作流程，解決 Shopify／宜搭 J2／J3 三系統的人工同步問題，並處理 BSMI 法規驅動的合規下架。

**角色**：需求定義、系統設計、實作、事故處理（獨立作業，正式生產環境）
**期間**：`【待填：起訖月份】`

---

## 1. 問題

一件商品下架，需要有人**同時在三個系統操作**：Shopify、宜搭 J2、宜搭 J3。

漏掉任何一個，就會出現「網站上還買得到但庫存系統已下架」這類不一致。而 BSMI（商品檢驗）法規要求的下架是**重複發生**的事件，不是一次性專案。

同時，站上還有 19 篇 PageFly 產生的遺留技術債文章需要清理。

`【可補：下架一件商品原本要手動點三個後台、大約花多少時間；有沒有發生過不同步造成的實際損失（超賣、客訴、稽核）。有具體例子會讓這段更有力。】`

## 2. 我的判斷

這裡我做了一個和前兩個專案不同的判斷：**這不是自動化問題，是系統邊界問題。**

三個系統各有各的資料擁有者，我不可能（也不應該）把它們合併。所以目標定為「讓跨系統操作變成一個動作，並且留下可稽核的記錄」，而不是「打造一個統一後台」。

## 3. 技術方案

**Shopify Embedded App**：React Router v7 + Prisma + Polaris/App Bridge，串接 Shopify Admin GraphQL API 與宜搭表單 API。

**為什麼自建而非用現成 SaaS 工具**：因為核心需求是**同步到宜搭 J2/J3**，而市面上任何現成的 Shopify App 都不支援宜搭（釘釘低程式碼平台）這端的整合——這是台灣＋中國企業系統的組合，沒有現成方案覆蓋。要讓「下架」變成一個跨三系統的原子操作，只能自建。

> 這是一個乾淨的 build-vs-buy 判斷：不是為了自建而自建，而是**現成方案在關鍵整合點上根本做不到**，評估後自建是唯一能滿足需求的路。

## 4. 這個專案真正特別的地方：AI 協作基礎設施

除了 App 本身，我建立了：

- **26 個 Claude Code skill**——把重複的營運操作（SEO 批次更新、商品封存、主題調整…）固化成可重複執行的標準流程
- **99 個 action 層級的 AI 工作日誌**（跨 29 個工作日）——每個操作留下做了什麼、為什麼這樣做的記錄

**這才是我最想談的部分。** 大部分人用 AI 是「問一次答一次」，我做的是把驗證過的流程沉澱下來，讓下一次執行不必重新解釋脈絡，也讓非我本人也能執行同一套流程。

這件事的本質是**知識管理與流程標準化**，和 PM 的核心工作高度重疊。

## 5. 三個決策取捨

**（1）Theme Editor 優先於改 code**
建立了十條防呆規則，凡是 Theme Editor 能做的一律不動程式碼。犧牲了一些客製彈性，換來的是**非工程人員也能維護**，且不會在 Shopify 主題升級時衝突。

**（2）查證後主動放棄一個需求**
首頁 meta description 的修改需求，我查證後判定 Shopify API 不提供這個能力，於是**主動回報「做不到」而非繞道硬改**。

> 硬改的方法是存在的（改主題檔案注入），但那會製造未來升級的地雷。我選擇讓需求方知道限制，一起決定要不要付這個代價。

**（3）平行化的效能取捨**
商品批次封存腳本平行化後，實測 114 筆／158.7 秒。平行度不是越高越好——太高會撞 Shopify API 的速率限制，反而更慢。

## 6. 事故與復盤（誠實揭露）

**2026-06-23 馬克杯文章覆蓋事故**：文章遷移時使用了更新（update）而非新建（create）操作，導致原文被覆蓋遺失。

`【待填：原文遺失多久？如何補救？有無業務影響？】`

**更值得談的是後續發現**：2026-07-13 我在整理記錄時發現，**這起事故當下沒有留下第一手記錄**——是事後補寫才察覺的稽核缺口。

**兩層修正**：
1. 流程層：內容遷移一律用「新建」，不用「更新」
2. 制度層：事故當下就要留記錄，不能等事後補。沒有記錄的事故等於沒發生過，下次還會犯

其他事故：商品圖裁切失誤、Windows 檔案佔用問題（重複發生 4 次後才根治）。
