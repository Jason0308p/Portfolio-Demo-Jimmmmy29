## 貫穿六個案例的三條主線（面試可主動點出的「一致性」）

- **AI 讓它做該做的、關鍵一步留給人**：讓 AI 大量處理可回復的工作，會直接動到正式營運（發布追蹤設定、覆蓋線上內容、報出價格）的那一步，一律由人確認才執行。
- **寫入前先查、寫入後回讀**：在會「出錯卻不報錯」的系統上工作，養成寫進去後一定讀回來比對的習慣，不靠系統回應判斷成敗。
- **數字誠實、可審查優先**：能佐證的和只是估計/待確認的分開標——不讓一個沒把握的漂亮數字，在面試被追問時破功。

# 01｜J1 商品文案自動化

**一句話**：把「電商新品上架的商品文案」這件重複、易錯、每個人寫法不一的工作，做成一條**可配置、可預檢、可追蹤、有防呆**的 AI 內容生產線——系統自動篩出還沒處理的新品，用累積下來的 SEO 命名規則生成名稱、描述、標籤；文字資料太少的商品，先讓 AI 讀商品圖辨識再命名；生成完直接寫回公司內部的釘釘宜搭表單，而且是在一個「寫錯不會報錯、會安靜失敗」的平台上把每一筆都寫對。

**技術棧**：Node.js（零外部相依，只用內建 fetch）· Claude AI 文案生成 · Claude 內建圖像辨識（讀商品圖辨材質品類，不需另接影像 API）· 釘釘宜搭 OpenAPI 串接（自建直連工具）· Claude Code Skill／自建工具（把規則與流程沉澱成模組）· PowerShell／BAT 排程自動化

**角色**：需求定義、規則制定、系統設計、實作、上線維運（獨立作業）　**期間**：`【待填】`

### 系統架構

整條生產線分五層，各司其職，彼此可獨立替換：

- **規則層（Skill）**：命名公式、關鍵字策略、描述的雙版本（給機器 / 給人）、各種硬性限制與一份自我檢查清單，全部沉澱成一份可累積、可審查的規則文件。規則怎麼調整都改這一份，不用改程式；別的品類、別的專案也能直接沿用。
- **資料連接層（自建串接工具）**：一套自己做的輕量工具，直接對接公司內部釘釘宜搭表單讀寫，不靠任何中間層或第三方服務。憑證與「會變動的表單／欄位對照」分兩處存放——以後多接一張新表單，只改對照設定、不動程式碼。提供查詢 / 新增 / 更新 / upsert / 刪除 / 觸發流程等完整操作。
- **寫入引擎（第一代，成熟）**：一次處理一整批商品的批次同步引擎：清理資料 → 寫入前檢查 → 逐筆比對表單現況 → 只更新有變動的欄位 → 失敗自動重試 → 寫回 → 產出報表與三層紀錄。欄位對照、模型名、固定值全部外部化到設定檔，換 SEO 欄位 / 切模型 / 停用某張表單通常只改設定。
- **生成自動化（第二代，原型）**：把「叫 AI 生成文案」這一步也自動化——用 BAT 啟動、PowerShell 控流程、直接以無視窗方式呼叫 Claude 生成文案、再交棒給 Node 同步。**不用人工開 AI 對話視窗**，可被排程器定時或批次觸發；生成完寫回表單這步仍複用第一代引擎。
- **圖片辨識分支**：文字資料很少的工單商品，這條分支先掃出商品圖網址，交給 Claude 內建圖像辨識直接讀圖、辨出材質與品類，再據此命名。

### 技術重點

- **AI 讀圖辨識命名（不需另接影像 API）**：對文字資料太少、光靠欄位命不出好名字的商品，先掃出商品圖的網址，直接交給 Claude 的內建圖像辨識能力讀圖，辨出材質、品類、特徵，再拿辨識結果生成名稱。整套辨識不需要另外申請或串接影像辨識 API。資料合併有明確優先級：**圖片看到的資訊優先於文字欄位**，兩邊衝突採信圖片，兩邊都沒有的一律留空、禁止編造。
- **自建直連公司系統的串接工具（零依賴、無中間層）**：自己做一套工具直接串接釘釘宜搭表單的 OpenAPI，只用 Node 內建 fetch，不引入任何第三方 SDK 或整合平台。憑證與「會變動的欄位對照」分層存放，新增表單只改設定不動程式——把公司內部系統的讀寫能力，變成自己可控、可擴充的模組。
- **命名規則引擎（可重複套用、可持續調整）**：把整套 SEO 命名邏輯——命名公式、關鍵字策略、硬性禁則、以及一份寫入前逐條自我檢查的清單——沉澱成一個獨立規則模組，而不是散在程式或某個人腦裡。規則改一次，全批次立刻套用；因為刻意做成從商品原始資料推斷（見決策 E），這套引擎不綁單一品類，能通用到玻璃杯等其他品類。
- **防呆寫入機制：只寫有變動的欄位（不亂覆蓋）**：寫回前先把表單現況整筆拉出來，跟要寫的內容逐欄比對，一模一樣的跳過、只寫真的有變的欄位。避免把沒動過的欄位反覆覆蓋，也避免誤刷生成日期。
- **防呆寫入機制：寫入前先檢查欄位存在**：真正寫回之前，先靜態驗證每一個要寫的欄位在表單上真的存在、必填資料沒缺、序號不重複；只要有一項對不上就直接中止、整批不寫。這是把「寫到一個不存在的欄位」這種錯，在源頭就擋掉。
- **防呆寫入機制：寫入後立刻讀回確認（這系統的關鍵）**：宜搭有個危險特性——當你寫到一個過期或不存在的欄位，它**不報錯、當作沒寫、卻回你「成功」**。所以寫完立刻把值讀回來、跟原本要寫的比對，一致才算數。這套「寫後回讀」不是預防性設計，是被**兩起真實的靜默失敗事故**打出來的（見下方事故）。
- **兩段式安全寫入（先預覽、加確認才真寫）**：預設只跑「預覽模式」，產出一份「這批會寫成什麼」的報表給人審；確認沒問題、加上明確的執行指令後，才真的寫進表單。把「寫錯了收不回來」變成「先看清楚再動手」。
- **自動化觸發（無視窗、可排程）**：AI 生成這一步做成可被 BAT／排程器自動觸發、不需要人工開著 AI 對話視窗，適合定時批次跑；批次會一路跑到沒有待處理商品才停。
- **失敗自動重試**：寫回失敗會依重試政策自動再試幾次，不是一次失敗就整批放棄。
- **全程可追溯紀錄（三層）**：每一批的讀取、生成、寫入都自動落成三層紀錄——當日日誌、累積統計、給主管看的摘要；任何失敗都必須寫明原因，不准安靜略過。回寫的資料還附上可點擊的來源網址，事後任何一筆都查得到來龍去脈。

### 核心設計決策

每一個都能說出「為什麼這樣決定」，其中一個是**推翻自己前一版**：

- **篩選條件兩次收緊——先搞懂資料再定規則**：一開始拿某個狀態欄位當篩選條件，後來發現它其實是「商品生命週期狀態」（會隨進度不斷變動），拿它當來源篩選會漏抓商品。於是改成「只有狀態是『已取號未上架』的才進流程」，其餘一律跳過。重點不是多加規則，是先理解資料本身的語意，再定規則。

- **通用行銷詞從「限量」升級到「完全禁止進名稱」**：「客製LOGO／企業贈品／OEM／批發」這類詞，一開始允許放一兩個。後來發現商品名普遍被這些詞灌爆、甚至一個名字塞兩個，稀釋掉真正的核心關鍵字。判斷是：這些詞每一家供應商都能寫，對搜尋零區別力，塞進名稱只拉低搜尋精準度。於是改成一律不進名稱、只放描述——不是砍掉這個賣點，是把它放到對的位置。

- **命名法從「規格堆疊」改「場景／問題前置」**：原本是把規格詞一路堆上去。改成命名前**強制先定義**「誰會用、什麼時候用、解決什麼問題」，把商品名第一個詞換成「客人遇到這問題時腦中會浮現的詞」，而不是廠商眼中的規格詞。等於從供給端語言轉成需求端語言。

- **四項命名紀律再收一輪**：同一天再加四條硬規則——一個商品只用一個主品類詞（禁止近義詞堆疊）、材質統一寫法、容量只寫單一數值（禁止範圍）、強賣點放前面。都是為了可讀性與搜尋精準度，也避免誤導消費者（例如單層杯不准標「保溫」，否則變成不實宣稱）。

- **外部關鍵字庫「先引入、再移除」（推翻自己的決定）**：某一版為了提升命名品質，特地建了一份「保溫杯」品類的外部關鍵字對照庫。用了之後判斷：這份字庫只服務單一品類，換到玻璃杯或其他品類就不通用、還要額外維護。於是下一版把它整個移除，改成「直接從商品原始資料（原始名稱、材質、英文原名、標籤、分類）自己推斷消費者會搜的詞」。這是「通用性 vs 單一品類最佳化」的取捨——明知短期文案品質可能略降，仍選擇一套規則能通用多品類的長期可維護性。

- **描述做成「給機器」和「給人看」兩個一致版本**：描述維護兩版，一版帶排版標籤給系統上架用、一版是純文字換行給人閱讀，但兩版內容完全一致、只差有沒有標籤。避免「兩套文案各說各話」，也讓內容可以互相對照追溯。

### 關鍵數字

- **累積 11 批 / 83 件 / 成功 83 / 失敗 0（100% 寫入成功）** ✅可佐證。誠實界線：這是**第一代通用批次同步引擎**的正式戰績，**不是第二代自動化原型**的成績——第二代目前還是單筆、預設只預覽的原型，沒有自己獨立的正式成功數字，它寫回表單時複用的正是第一代引擎。
- **單次最大批量 25 筆 ×2**（同一天兩批） ✅可佐證。
- **保溫杯 11 筆**是打磨命名規則用的手動實驗批、經過多輪重跑，屬規則實驗場，**不計入上面的 83 件** ⚠️自測值。

### 事故驅動的防呆（為什麼「寫後回讀」是硬需求）

- **事故一**：J1 表單新增 AI 欄位後，更新舊記錄時平台用了快取的舊 schema，新欄位值被**靜默忽略**——回應仍顯示成功、欄位卻是空的。修法是每次寫入強制帶「使用最新版本」旗標，並固化進引擎預設。
- **事故二**：某個 HTML 欄位的設定 key 根本不存在於表單，導致之前所有批次寫 HTML 全部**靜默失敗**（沒噴錯、以為成功），事發後才被發現。修法是換成正確欄位、補寫、並**把值讀回來比對長度**確認才算數。
- 這兩起同型事故（平台對「schema 過期 / key 不存在」一律靜默）共同導出一條流程強制項：**在一個會靜默失敗的系統上，回應「成功」不代表寫進去了，唯一可靠驗證是把值讀回來比對**。這條紀律後來延用到其他專案。

### PM 力展現

- **把問題定義對**：拒絕把它當成「打字太慢」的效率問題，定義成「商品文案品質與一致性」的問題——正因為這樣定義，後面所有可累積的規則才有意義。
- **判斷力可審查**：六個命名決策每一個都能說清楚「為什麼」，還包含一次公開推翻自己前一版（外部字庫引入後又移除）——這正是面試最想聽的取捨敘事。
- **資料模型優先**：從「篩選欄位語意搞錯導致漏單」這個坑，養成「先理解資料本身、再定規則」的習慣，而不是一直疊新規則去補。
- **通用 vs 特化的架構取捨**：明知短期文案品質可能略降，仍選擇跨品類都能用的推斷法，用長期可維護性換掉眼前的一點效果。
- **事故驅動的紀律**：兩次「明明失敗、系統卻回報成功」的靜默寫入事故，復盤出「寫後一定讀回來確認」這條流程，並延用到其他專案——沉澱下來的是可複用的流程，不是一次性補丁。
- **對脆弱系統設防呆**：在一個「寫錯不會報錯、會安靜失敗」的平台上，把「寫入前檢查」和「寫入後讀回」做成流程強制項，而不是傻傻相信系統回報的成敗。
- **誠實區分成熟與原型**：主動釐清兩代界線，83 件只算第一代的成績，不把還在原型階段的第二代成效灌水成戰績。

> **誠實缺口（對外展示前須修）**：repo 有三處殘留錯誤需要修——第二代的篩選條件還停在舊版（沒跟上「已取號未上架」的定案）、給主管看的文件裡殘留一個已作廢的錯誤欄位設定、文件裡的流程清單名稱和實際資料夾對不上。

# 02｜營運流程自動化

**一句話**：把一間只靠人腦和 Excel、沒有資料系統的傳產轉電商公司，一條一條帶進自動化——一個人從需求盤點、排序、動手實作到跨部門推行全包。

**技術棧**：n8n 流程自動化 · Python 自建串接程式 · Meta／Threads 官方 API · 釘釘宜搭 OpenAPI · QR Code 流程追蹤

**角色**：需求盤點 · 決定先做哪一條 · 流程設計 · 動手實作 · 跨部門推行（全程獨立作業）　**期間**：`【待填】`

### 系統架構

這個案子是三條各自獨立的營運流程，我一條一條數位化：

- **社群數據回寫**：自寫程式串 FB／IG／Threads 三平台官方 API，把三邊格式各異的貼文成效，自動對應進公司內部釘釘宜搭表單、定期刷新回寫。這條有完整程式碼、可實際展示。
- **貨運 QR Code 全流程**：收貨 → 驗貨 → 加工 → 出貨四環節，用掃碼串成一條可追蹤的流程。
- **財務月結重設計**：拆分帳戶功能、做表單連動與異常通知，讓會計月底結帳不用再整天人工比對多張表。

三條共用同一套工具分工原則：需要視覺化、要快速把多個服務串起來觸發的用 n8n；需要穩定、能搬機器、能測試的抽成 Python。常見演進是先用 n8n 做原型快速驗證，跑穩後把核心邏輯改寫成 Python、掛正式排程長期跑。

### 技術重點

- **自建三平台資料串接管線**：自己寫程式直接串 FB（Page feed）、IG（media）、Threads 三個平台的官方資料介面。三邊回傳的欄位結構、命名、資料型別都不一樣，我做了一層自建轉接，把它們統一對應到公司內部宜搭表單該有的欄位，再透過釘釘宜搭 OpenAPI 定期刷新回寫。重點是「一套自建串接層吃多平台、把不同格式統一收斂成公司系統要的單一乾淨樣子」。
- **抓取到寫回是一條完整管線**：從各平台 API 拉貼文（內文、發布時間、連結、互動數、圖片、hashtag），經過轉換層清洗——內文做 HTML escape、換行轉標籤、hashtag 用規則抽取、輪播貼文取代表圖——最後以「認得出同一篇貼文就更新、認不出才新增」的方式寫回宜搭。表單不會愈跑愈肥，數字永遠是最新的。
- **從視覺化流程工具真實遷移到自寫程式**：這條流程原本是用 n8n 在畫布上拉線做的，後來我把整條改寫成 Python 版。動機是 n8n 綁在特定主機上，Python 版可以整包複製、搬到任何機器上獨立排程跑，也能寫測試驗證。兩個版本我都留著可對照——這是我對「同一條流程做過 n8n → Python 完整遷移」最扎實的證據。
- **刻意零第三方依賴、可搬移**：串接程式只用語言內建的網路庫，不裝額外套件，複製到新機器就能直接跑，不用先花時間佈環境。網路連線失敗時內建自動重試，不會一次連不上就整條斷掉。
- **懂平台 API 的邊界**：FB／IG 的互動數是我從官方 API 真的抓回來的，而且會受帳號 token 權限影響能不能拿到；Threads 官方 API 目前不開放對應數值。我能清楚區分「這是平台真給的數據」和「這是平台不開放、只能留位置」，不會把兩者當成同一種可信度混著講。
- **遷移時順手砍掉死流程**：舊 n8n 版裡有一段接到別的購物平台、但其實根本沒真的寫回任何地方的殘留分支。改寫時我把它整段移除，只留下真正有用的三平台回寫。重寫是清理死路徑的好時機。
- **排程知道邊界**：程式雖然內建「自己一直開著跑」的選項，但我在文件裡註明正式環境應交給作業系統的正規排程工具定時觸發——因為一支程式自己長時間開著不關，久了容易出狀況。
- **貨運 QR Code 串起四環節**：收貨、驗貨、加工、出貨原本各自獨立、無串連。我為每環節設計獨立表單（收貨記時間品項、驗貨記規格與工時、預計到貨、出貨記裝箱數與郵寄狀態），用 QR Code 把各環節表單連起來、觸發表單連動與自動通知。業務掃一次碼就能看到該筆貨在各環節的完整資料，狀態也自動帶到下一階段。附帶做了兼職計時與薪資換算的儀表板。
- **財務月結流程重設計**：把原本各自獨立的多個銀行帳戶、收付款、零用金、支出表，重新拆分帳戶功能並做資料連動——會計輸入一筆交易後相關表單自動更新，再加上總表彙整、異常即時通知與多人查改權限。（這條我沒有留下可展示的程式碼，定位為流程與營運面的重設計，不宣稱技術實作深度。）

### 核心設計決策

- **工具分工，不是二選一**：確定性的規則、需要測試把關的邏輯走 Python；需要視覺化編排、把多個服務串起來觸發的走 n8n。兩種各有位置，看任務性質分配，而不是全押一邊。同一條社群流程我就是先用 n8n 出原型驗證，跑穩後把核心邏輯改寫成 Python 上正式排程。
- **為什麼先做貨運和財務**：這兩條都同時命中「一直重複發生 × 規則很明確 × 出錯代價很高」。一直重複，省下來的時間才會複利放大；規則明確，機器才接得住；出錯代價高，自動化就同時是在降風險。
- **排順序本身就是 PM 的工作**：資源就我一個人，決定「先做哪一條、為什麼是這個順序」，比「全都想做」更重要。
- **敘事按證據強弱排**：先講最經得起檢驗、有程式碼可看的社群這條；成果敘事和技術證據我分開講、不混為一談。

### 關鍵數字

- **社群同步**：一套自建串接層自動把三個平台的貼文數據對應進公司表單、定期刷新回寫，同一篇不重複堆疊。✅ 這條有完整程式碼可實際展示。
- **貨運內部確認時間 −50%**：`【待你確認】`（履歷檔曾寫過，但我沒有親自量測、也沒有前後對照數據，所以不逕自寫進成品）
- **財務人工作業量 −50%**：`【待你確認】`（同上，履歷曾寫、未經量測佐證）
- **財務月結 從 1 天縮到 2 小時內**：`【待你確認】`（同上，履歷曾寫、未經量測佐證）
- **每月省下 20+ 小時人工**：`【待你確認】`（履歷曾寫，但沒有拆解各條流程各佔多少，也未經量測佐證）
- **貨運查詢 從數小時 → 即時**：質性描述保留（業務原本被客人問「貨到哪了」答不出、要拜託貨運去查；掃碼後當場就能看到），但不掛具體百分比。

### PM 力展現

- **排序判斷**：面對老闆「什麼都想數位化」，我不照單全收，而是用「重複發生 × 規則明確 × 出錯代價高」三個準則，排出應該先做哪一條。
- **跨部門推行不靠職位壓人**：貨運 QR Code 這條，我先做一個能掃、能看到貨況的小原型，丟給倉庫同事實際試用，好用了再回頭說服比較保守的業務端——由下而上擴散，化解傳產轉電商裡各部門的觀望。
- **從共同痛點切入**：業務痛在被客人問貨況答不出來，倉庫痛在不知道貨到哪一站；我把方案定位成「一次解你們兩邊的痛」，而不是「上面交代的新規定」，大家才願意用。
- **懂平台的邊界**：我能清楚區分「平台真給的數據」和「平台不開放、只能先留空的位置」，不會把兩者混為一談當同一種可信度講。
- **誠實標注數字**：我主動點出一個結構性錯配——最漂亮的商業數字落在沒有程式碼佐證的貨運／財務兩條，而有完整程式碼的社群這條反而沒有響亮數字。這個實話我選擇講出來。
- **不硬湊數字**：貨運／財務的省時數字我沒親自量測、也沒有前後對照，就一律標「待確認」，絕不硬套到有程式碼的那條上去借光。
- **主動揭露待驗證項**：社群這條我自己就標出還沒完全驗證的點（一個新增的備註欄是否真的存在於後台、社群互動數字準不準取決於帳號權限），實際展示前應先回後台確認過。

- **自建並行批次工具，逐筆慢跑改成大批快跑**：一件商品要下架，得在三個系統各操作一次（Shopify 改狀態、宜搭 J2、宜搭 J3）。我把這三步合成一鍵，並把執行引擎從循序版（單執行緒、每筆約八次 API 來回）改寫成 8 執行緒並行版——批次先查商品 id、8 條並行、宜搭用單次 insertOrUpdate、事後抽樣回讀。實測一批 148 件約 3.4 分鐘、148／148 成功 0 錯，換算單筆從循序的 14.4 秒縮到並行攤提後約 1.4 秒，**快約 10 倍**。工具支援斷點續跑與 CSV 進度存檔，避免長批次撞工具逾時就前功盡棄。
- **中文搜尋治理**：網站用的商業主題原生中文分詞差，加上前綴比對放大噪音，搜「保溫杯」會回一堆不相干商品；而 Shopify Admin API 沒有公開的同義詞介面，不能直接把同義詞推進原生引擎。我先做客戶端同義詞字庫＋OR 展開（擴大比對），撞到 Shopify 搜尋解析器的布林上限（OR 詞達 11 個直接回 0 筆）後，聽懂使用者要的是「更精簡準確」而非「更多」，整套翻轉成精準收斂——關掉字庫、限定只比對商品標題欄位、在瀏覽器端幫每張商品卡算分（標題＋10／類型＋5／標籤＋3）重排、加上「搜尋：X（N 筆）」標頭，把同一關鍵字結果從 359 收斂到 232 筆（−35%）。
- **把重複店務技能化、可交接**：把重複的營運操作沉澱成 **7 套自建營運技能**（工作日誌規範、集合圖生產線、頁面區塊設計系統、舊文章清理、SEO／GEO 成長策略、釘釘宜搭表單操作、上線前強制確認）＋近百筆（101 筆）可追溯的逐案工作日誌。這讓 AI 能當執行工具，可重複、安全地做店務，換人接手也讀得懂、跑得動（另有 Shopify 官方隨附的參考範本，不計入這 7 套自建）。
- **改店一律照非破壞式流程**：碰主題碼前先查 Theme Editor 設定、對照 Dawn、才做最小改動；改 live theme 前一律 `themeDuplicate` 留備份，正式站改動只切最小檔案並在上線後用 curl 線上 HTML＋無頭 Chrome 截圖驗證——驗線上而不是驗本機檔。
- **集合封面圖生產線**：把「生成→上傳→回頭檢查真的成功」封裝成一套可續跑的標準流程，跑 15 個批次、每批 10 張，最後做到 360／360 集合全部有圖。
- **搜尋引擎結構化標記與健檢**：修首頁 OG 分享縮圖、改寫 JSON-LD 的 canonical、補 H1 與 meta；再配一支唯讀健檢工具掃全站頁面／文章／集合缺漏＋商品抽查，供每月對比。（純結構化標記，沒有裝流量追蹤碼、沒做銷售報表——那是 04 的 GA4 案例。）
- **全站營運的深度覆蓋**：除上述外，商品自訂欄位、集合、篩選器、內容頁、SEO 一路做到全站十六面向，廣度本身就是這個專案最強的賣點。

### 核心設計決策

- **搜尋策略整個翻轉（擴大→精準）**：第一版做「擴大比對」抓更多結果，方向錯了 → 聽懂使用者其實要「更準更精簡」，把做好的整套同義詞 OR 展開丟掉重寫成收斂策略（359 → 232 筆，−35%）。因為每一版都留了可回滾的備份和完整決策記錄，砍掉重練的成本很低——這正是我堅持寫工作日誌的理由。
- **法規下架該買現成還是自建**：BSMI 合規下架牽涉 Shopify＋公司內部釘釘宜搭 J2／J3 的三方同步，市面現成 App 沒有一支能接到我們內部那套表單系統 → 只能自建，才能讓「跨三個系統的下架」變成一個原子動作、還留下稽核記錄。不是為了自建而自建。
- **一次事故變成一條制度**：早期做文章遷移時，用「更新文章」（articleUpdate）蓋掉了原文導致遺失 → 立下「遷移／複製一律用『新建文章』（articleCreate）、不覆蓋原文」的鐵則，重做時改成 19 篇 `static-` 前綴複製版本、19 筆全部成功。事故換來的紀律（遷移一律新建、寫前讀現值、寫後回讀、上線驗線上）比多一個功能更值錢。
- **查清楚做不到就誠實放棄，不硬湊**：首頁 meta description 有個錯字要改，查證後確認 Shopify 現行 Admin API（REST／GraphQL）根本沒有介面能讀寫首頁這個欄位 → 不用「改全站共用版型硬蓋」這種高風險 workaround 湊一個「看起來完成」，而是把它降級成一個 30 秒的後台人工步驟並附上正確全文交回。同一份任務裡能安全做的（首頁 H1 補字，先備份再改再驗上線）就做完，做不了的誠實回報。

# 04｜GA4 + GSC + GTM 跨源數據儀表板

**一句話**：把散在三個後台、互不相通的網站數據——網站行為、Google 搜尋成效、追蹤設定本身——串成一份自動產出、中英雙語、給不會開後台的主管也看得懂的互動報表；並自建一套讓 AI 能直接讀寫追蹤設定的工具，把原本人工一格一格點的設定變成對話式操作。從「設計要追蹤什麼」到「產出洞察」一條完整落地。

**技術棧**：GA4 Data API（網站行為）· Google Search Console API（搜尋成效）· Google Tag Manager API v2（追蹤設定）三方 API 整合 · 自建 MCP Server（讓 AI 能直接操作追蹤設定的工具，Python FastMCP 寫成）· AI 自動產生中英雙語儀表板 · Plotly 互動圖表（趨勢／漏斗／熱力圖）· 前端純 HTML/JS

**角色**：需求定義／追蹤架構設計／MCP 工具開發／儀表板產品化（獨立作業，現職） **期間**：`【待填】`

### 系統架構

三個數據來源各管一塊，先各自把資料抓回來、對齊口徑，再由程式自動組成報表：

- **網站行為（GA4）**：訪客做了什麼、看多深、詢價漏斗走到哪、從哪裡來（含被 AI 助手引薦進站）。
- **搜尋成效（Search Console）**：在 Google 上被哪些關鍵字搜到、曝光、點擊、CTR、平均排名。
- **追蹤設定本身（GTM）**：網站到底在收哪些數據——這一塊是設定，不是報表，透過自建工具讓 AI 能直接讀寫。

資料流是一條完整 pipeline：三個 API 各自把原始資料抓回來、落檔存成 JSON → 一支自動產表程式把三邊的時間區間、統計口徑對齊（避免三邊數字兜不起來）→ 一次產出中英雙語互動報表 → AI 讀這些資料，自動寫出四個分頁的洞察（整體成效摘要、SEO 機會、轉換分析、AI 引薦流量）。另有一套自建工具讓 AI 回頭把缺的追蹤補齊。

### 技術重點

- **自建讓 AI 能直接操作追蹤設定的工具（MCP Server＝讓 AI 能呼叫外部工具的一種標準介面）**：原本設定網站追蹤要人工進 GTM 後台一格一格點，我用 Python 自己寫了一支工具，把「列出／新增／修改／查詢追蹤標籤、觸發條件、變數」封裝成 13 個 AI 能直接呼叫的動作（7 個讀取、4 個新增、5 個修改／取單），讓 AI 能自己「列出目前所有標籤 → 判斷缺哪個事件 → 直接建好」，把設定追蹤從人工點擊變成對話式操作。（追蹤標籤＝告訴系統「這個按鈕被點了要記一筆」的一小段設定）

- **三方數據源整合成一份報表**：把網站行為（GA4）、搜尋成效（Search Console）、追蹤設定（GTM）三個原本互不相通、各自要開後台拉報表的來源，透過各自的 API 抓回來、對齊維度與口徑，串成同一份自動產出的中英雙語互動儀表板，讓不會開後台的主管、行銷也看得懂。

- **按商業問題設計追蹤，不是隨手全開**：先想清楚每個追蹤要回答什麼商業問題（例如「詢價單有多少人送出」「LINE 按鈕放哪個版位最有效」「客人卡在漏斗哪一步」），再據此設計要收哪些使用者行為事件（使用者行為事件＝訪客的每一個動作，例如點擊、捲動、送出詢價）。最後真的在收的行為事件共 32 個，涵蓋內容看多深、站內搜尋、篩選排序、詢價轉換、LINE 各版位效益——每一組背後都對著一個要回答的決策。

- **詢價與 LINE 的追蹤刻意拆細，才數得清成效**：送出詢價單獨立埋成專屬轉換事件，不跟一般表單混在一起，才數得清核心成效（近半年 750 次）；LINE 按鈕刻意拆成五個版位（header／footer／產品頁中段／聊天鈕／曝光）分開追蹤，就是為了判斷放在哪個位置最有效。

- **AI 引薦流量歸因（前瞻的新流量來源）**：追蹤有多少訪客是被 ChatGPT／Claude／Gemini／Perplexity 這類 AI 助手推薦進站的——做法是抓每個訪客進站前的來源網域，把這些 AI 助手的網域分類出來單獨歸因。在 AI 搜尋逐漸吃掉傳統 Google 搜尋的當下，這是很多網站還沒開始看的新流量來源。

- **追蹤設定的實際規模**：整套追蹤裡有 17 個追蹤標籤、16 個觸發條件（觸發條件＝什麼動作發生時才記一筆，例如點擊、元素露出、捲動到某深度）、9 個變數（變數＝記錄時要一起帶上的資訊，例如點了哪個篩選器、篩選價格區間），皆為真實生產環境的匯出設定。

- **各種互動圖表由程式自動產出、中英雙語同一套邏輯**：趨勢圖、轉換漏斗、星期×時段熱力圖、關鍵字溫度圖、裝置圓餅圖等，全由產表程式自動生成，中英兩種語言版本由同一套程式邏輯產出——禁止只改單一語言版，把「雙語永遠一致」從靠人記得變成程式保證。一次產出八頁：中文、英文各三個時間窗（近 30 天／近 180 天／預設）＋一份對外用的去識別公開版＋一頁總覽。

- **報表是自動產出物，立紀律不准手改**：報表 HTML 一律由產表程式生成，訂下「不可手改、要改就改產表程式」的規矩——避免下次重跑被蓋掉、或手改單一語言版導致中英走鐘、新舊程式並存整頁圖表失效。

- **踩過並解掉兩個登入授權的坑（不是查文件查得到的常見坑）**：其一，抓網站行為（GA4）和改追蹤設定（GTM）若共用同一組登入授權，Google 會把後授權的把先前的授權踢掉，症狀是「授權完 GTM 就說 GA4 授權失效、反過來也一樣」的鬼打牆——必須讓兩邊各自用獨立的登入授權才互不干擾。其二，用某種通用的登入方式去抓網站行為資料會一直被拒絕（回報權限不足），即使看起來已經登入成功，得改用專屬授權重新登入才打得通。兩個都是實際踩到才解出來的。

### 核心設計決策

- **只給 AI 改的權限、不給發布上線的權限**：這套工具刻意設計成 AI 只能把設定改在「草稿區」，不能按下發布上線——授權範圍刻意只給「讀取」與「編輯草稿」，就是不給「發布」。所有改好的追蹤設定，一定要人工在後台檢視過，才由人按下最後那個發布鈕。讓 AI 提效率、人守最後一關——這跟我在 Shopify、J1 上架兩案的做法一以貫之：可逆的動作交給 AI，不可逆的上線留給人。

- **改設定前一定先讀回現況**：修改追蹤設定是「整包覆蓋」的（送新的會蓋掉整筆而不是只改一欄），所以工具強制「先把現有的完整設定讀回來 → 在上面改 → 再整包送回」，避免漏掉沒動到的欄位而把別人設好的設定改壞。

- **先定好資料規範再擴功能**：先把頁面類型、互動類型、行銷活動來源（含 chatgpt／claude／perplexity 這些 AI 引薦來源）的命名規範定下來，再往上加追蹤——避免數據長到後來一堆來源分不清、變成一坨「不明來源」。

### 關鍵數字

- ✅ **可佐證（近 180 天真實資料）**：32 個實際在收的使用者行為事件；近半年網站瀏覽約 82 萬次；送出詢價單 750 次。
- ✅ **可佐證（追蹤設定實際匯出）**：17 個追蹤標籤／16 個觸發條件／9 個變數，皆為真實生產環境設定。
- ⚠️ **待本人核算口徑**：核心關鍵字 Google 搜尋排名 15→7、自然搜尋曝光 +30%、廣告花費 −30%——這三個數字需再核對前後對比區間、是全站還是特定關鍵字群、以及歸因邊界後才可正式引用，此處先不裸寫為已證實成果。
- 線上 demo 用的是**示意用的假資料**（去識別、非真實帳號數據），AI 分析分頁為前端模擬呈現、非即時呼叫 AI，展示時會主動標明。

### 圖表代表作（每張對應一個決策問題）

- **搜尋成效三軸組合圖**：曝光（面積）＋ 點擊（長條）＋ 排名線三軸疊在一起，排名這條刻意上下反轉，讓「線往上＝排名進步」，主管一眼看不會看反。
- **雙轉換漏斗並列**：對照不同路徑的轉換，看客人卡在哪一步流失。
- **星期 × 時段熱力圖**：回答「什麼時候投廣告、發文最有效」。
- **AI 引薦流量歸因**：追蹤有多少訪客是被 ChatGPT／Claude／Gemini／Perplexity 推薦進站——在 AI 搜尋逐漸取代傳統搜尋的當下算前瞻維度。
- **關鍵字溫度圖**：關鍵字表格依各欄位數值高低自動上色，一眼看出哪些字表現好。
- **進站頁長條圖標色疑似機器人流量**：代表有在判讀流量品質，不把灌水流量當真流量。

- **把技術產品化**：自建一套 13 個動作的工具，把「只有工程師會進後台操作追蹤」變成 AI 能對話呼叫；三個互不相通的後台，最終收斂成一份給不會開後台的主管、行銷也看得懂的報表。

- **先定資料規範再擴功能**：命名規範與行銷活動來源慣例先行，資料先完整、口徑先一致，再談怎麼呈現。

- **可審查性優先於好看**：三個搜尋成效數字明確標「待本人核算口徑」、線上 demo 主動標成假資料——寧可標清楚，也不把沒核實的數字裸寫成已證實成果。
- **把易錯處變成硬規則**：報表不可手改、雙語同源產出、改設定前先讀回現況——把最容易出錯的地方寫成強制流程，而不是靠人每次記得。

# 05｜台股輿情分析系統

**一句話**：一套本地端到端的台股輿情系統——自動從 9 大類、83 個不同來源（社群／新聞／YouTube 逐字稿）蒐集討論，用「關鍵詞規則先篩、AI 再判」的兩層架構把 AI 成本壓到最低，每天產出多時間區間的情緒報告，自建 Email 驗證碼登入保護後發布上線並推 Telegram 警示；已連續運作 2 個月、累積 35,597 則貼文 / 36,760 筆情緒評分。

**技術棧**：Python · Whisper（faster-whisper 語音辨識）· Playwright（瀏覽器自動化）· yt-dlp · Claude Haiku（本地 CLI）· SQLite · Cloudflare Workers + D1 雲端資料庫 · 自建 Email OTP 登入（HMAC 簽名 session）· Telegram / Gmail 推播

**角色**：系統設計 · 多來源蒐集 · AI 分析架構 · 前端發布與權限控制（獨立作業，個人專案做到 production）　**期間**`【待填】`：自 2026-05-21 連續運作約 2 個月

### 系統架構
- **蒐集層**：83 個來源用一套共通框架統一抓取，內建自動容錯（被封鎖或憑證失效的來源自動略過），不同來源依特性用不同抓取管道（RSS、逆向 API、瀏覽器自動化、語音辨識）。
- **判定層（兩層）**：先用關鍵詞規則在本地免費判定情緒，規則判不準的才升級交給 AI。
- **成本層**：AI 跑在固定月費方案（用量再大也不加價），再從「壓縮每次呼叫的固定開銷、選最便宜模型、批次分攤」三方面把成本壓到最低。
- **輸出層**：產出 5 個時間區間的情緒報告 → 多管道發布（登入制網站／Telegram／Email）＋雲端資料庫（Cloudflare D1）同步，供線上即時查詢 API。
- **編排層**：一條主流程支援多種執行模式（完整跑／只跑社群即時／只掃新聞／只跑 YouTube／只重出報告）＋定時排程＋來源冷卻避免重複抓取。

### 技術重點
- **多來源統一蒐集框架**：把 83 個性質各異的來源（PTT 股板、57 個財經新聞 RSS、YouTube 頻道、Threads、鉅亨網、CMoney、Google 搜尋熱度…）用一套共通抓取框架整合，要加新來源只需接上、不必重寫；repo 實際寫了約 20 個獨立來源整合，能力廣度超過目前上線的量。
- **壞格式自動修復**：57 個財經 RSS 中不少 feed 回傳格式殘缺或壞掉的 XML，抓取層在標準解析失敗時自動改用 HTML 解析器兜底把資料救回來，並對整批死掉的 feed 設 30 分鐘 TTL 略過，不讓單一壞來源拖垮全流程。
- **逆向串接無公開 API 的來源**：鉅亨網沒有公開資料介面，逆向出它的內部 REST API 並補上必要的 referer header 自己接；Dcard 則逆向其行動 App 的私有 API（帶特定 client-type header 偽裝）——不受限於「有沒有官方 API」。
- **瀏覽器自動化抓需登入的動態頁**：Threads、CMoney 這類要登入或靠 JS 動態載入的頁面，用 Playwright 瀏覽器自動化＋注入登入 cookie 模擬真人操作（自動捲動載入更多）才抓得到，突破純 HTTP 抓不到的內容。
- **繞過 YouTube 機器人偵測抓字幕**：YouTube 用 PoToken 擋自動抓字幕（官方套件被擋到回 200 但 0 bytes），改用 yt-dlp 模擬 Android／TV 裝置的內部端點繞過「請登入確認你不是機器人」的機器人牆，成功取得逐字稿。
- **Whisper 語音辨識補無字幕內容**：很多影片與直播（例如股癌 podcast）根本沒有字幕，改用 yt-dlp 抓最佳音檔、送 Whisper 開源語音辨識模型（faster-whisper）轉成逐字稿，長音檔分段處理——連沒有現成字幕的內容都能一併納入分析。
- **兩層情緒判定（核心）**：先用一套關鍵詞規則在本地免費判斷每則貼文——比對情緒詞（正負向分 6 級加權）＋事件詞（財報／漲停／升息等 10 類），命中詞前方出現「不／沒有／未」等否定詞會自動反轉語意，命中「暴／狂／崩／飆」等強烈用語會加權放大——明顯的直接定案，只有規則判不準的才交給 AI 做語意分析。凡帶重大事件標籤的貼文一律送 AI，寧可多花一次也不漏掉會影響股價的訊號。
- **AI 呼叫框架開銷砍約 80%（省最多的一筆）**：AI 走固定月費方案（用量再大也不加價），透過關掉 AI 內建的一整套預設工具與助手人設、只留真正需要的，把每次呼叫都要重複附帶的固定開銷砍掉約八成；再加上全程用最便宜的模型、一次批次處理多篇分攤成本，多層把 AI 花費壓到最低。
- **AI 韌性降級**：AI 回傳的 JSON 解析失敗時自動重試，兩次都失敗就降級改用本地規則層的結果備援，絕不讓整批貼文掉資料。
- **報告生成提速**：把原本要約 750 次資料庫查詢（N 股 × 5 窗口 × 3 種查詢）才生得出的每日報告，改成一次撈完 60 天資料在記憶體裡聚合計算，產出時間從數秒縮到 0.01 秒。
- **自動部署 pipeline**：本機產出 HTML → 自動推 GitHub 私有 repo → Cloudflare Worker 連動 Git 自動部署上線；同一條流程另增量同步近 14 天彙總資料到 Cloudflare D1 雲端資料庫，供線上 `/api/trending`、`/api/stock/:code/history` 即時查詢。
- **自建 Email OTP 登入系統保護線上報告**：白名單信箱才收得到 6 碼一次性驗證碼（用 Gmail API 寄、存 KV 10 分鐘失效）→ 驗證通過後發一組 HMAC-SHA256 簽名、7 天有效的加密 session cookie；登入閘門與 dashboard、查詢 API 全整合在同一個 Cloudflare Worker，未通過驗證一律擋在門外。自建的原因是現成的免費權限方案要綁信用卡。

### 核心設計決策
- **為什麼分兩層**：AI 呼叫是整套系統唯一「用越多花越多」的成本，目標是「只在真正需要語意判斷的地方花 AI」，其餘用免費規則擋掉——這是「知道何時不該用 AI」的產品判斷。
- **用真實數據推翻自己的初版假設**：最初估計規則層能省 6～8 成 AI 呼叫，但把兩個月的實際執行記錄拉出來一算，規則直接跳過的只有約 17%（社群貼文多半會命中個股關鍵字或帶情緒用語，很難同時滿足「中性＋無事件＋命中詞少」三條跳過條件）；於是往下再挖，發現真正省錢的其實是「壓縮呼叫框架開銷（33K→6K）＋換最便宜模型＋批次分攤」這幾招——不迷信初版設計，用數據找真因。
- **被網站擋時停損、不硬撞**：Dcard／Mobile01 連續被 Cloudflare 403 擋，判斷不值得用瀏覽器硬繞就停用；Google Trends 非官方端點約 8 個關鍵字後就限速，就降頻加冷卻、接受量少——連續被同類錯誤擋代表對方在防你，正確做法是放慢、換管道或停用，而不是把重試次數往上加硬闖。

### 關鍵數字
- 連續運作約 2 個月（2026-05-21 起）、42 份每日報告、35,597 則貼文 / 36,760 筆情緒評分、83 個不同來源（含 57 個 RSS、15 個 YouTube 頻道）、追蹤台股 61 支 / 26 族群、美股 54 支
- 情緒詞庫：正向 100 詞 / 負向 78 詞 / 事件標籤 10 類 105 詞
- 每次呼叫 AI 的框架固定開銷砍約 80%（33K→6K token）；規則層實際跳過約 17% 的貼文（初版誤估為 6～8 成，已用真實 log 校正）
- 報告產出從數秒縮到 0.01 秒（約 750 次查詢 → 1 次）
- 情緒分析準確率：無實際量測，不宣稱

### PM 力展現
- **把成本當產品變數在管理**：把 AI 呼叫視為唯一的變動成本，整個架構圍繞「怎麼少花、花在刀口上」設計，而不是無腦每則都丟給 AI。
- **用數據校準、勝過憑感覺**：親自把兩個月執行記錄拉出來驗證，推翻自己原本的省成本假設（6～8 成→17%），再挖出真正的槓桿在哪。
- **把系統韌性當常態設計**：預設「來源一定會不斷壞掉、帳號會過期、格式會殘缺」，讓任何一環失效都自動略過、不影響其他，整條流程不掉資料。
- **端到端 ownership**：從多來源蒐集（含逆向 API、瀏覽器自動化、語音辨識）、兩層判定、控成本、產報告、多管道發布到自建登入權限，一個人全部搭起來並實際上線運作。
- **誠實邊界**：沒量測的準確率不宣稱、用不實的預估數字（60～80%）不沿用，一律用真實 log 校正後的數字。

# 06｜LINE RAG 智能報價客服機器人

**一句話**：全站 1.6 萬商品的 LINE 官方帳號自動客服與報價機器人——用 RAG 檢索增強生成（讓 AI 先查公司真實的商品與牌價資料、再據此回答，而不是憑空生成），並靠多層檢索讓「客人給料號就毫秒級精準回、只有模糊問法才動用語意搜尋、查不到就明說要人工絕不亂報價」。

**技術棧**：Python · Gemini 生成（gemini-2.5-flash）+ 語意向量模型（gemini-embedding-001，把文字轉成一串代表「意思」的數字）· RAG 檢索增強生成 · 向量相似度搜尋資料庫（Qdrant，用「意思接近」而非「字面相同」來找資料）· LINE Messaging API

**角色**：需求定義 · 系統架構 · 產品邊界判斷（獨立）　**期間**：`【待填】`

### 系統架構

整套以 **RAG 檢索增強生成（讓 AI 查到公司真實資料後才回答）** 為底層方法：客人問題進來後，系統先去公司的商品庫、牌價庫、常見問答庫把「真實資料」撈出來，再把這些資料連同問題一起交給大模型組織成回覆——大模型負責「用人話講清楚」，不負責「憑空生出商品規格或價格」。

- **① 問題先分類（純規則，不動用 AI）**：訊息進來先用關鍵詞規則判斷客人要「找產品／問規格報價（FAQ）／兩者都要（mixed）」，這一步完全不呼叫大模型，省時省錢。
- **② 冷熱資料分層**：常用又要精準的資料（料號、分類代碼、中文別名對照）放在**本地記憶體快取**即時查，毫秒級就回；龐大、偶爾才用的全品項資料放在**向量相似度搜尋資料庫**，只有前面查不到時才動用。判準是查詢頻率與精準度需求——用得多、要精準的放本地（熱），用得少的放語意搜尋（冷）。
- **③ 找產品的多層檢索階梯（由快到慢，命中就停，不再往下走）**：料號精準查 → 分類代碼查 → 中文品類別名對照查 → 中文關鍵詞掃描 → 都查不到才動用語意搜尋。前四層全走本地、完全不需要把文字轉成向量；只有最後一層才真的去問大模型「意思最接近的商品是哪些」。
- **④ 報價邏輯**：價格依「料號 × 訂購數量級距」分層存放，客人給了數量，就在**同一個料號**底下挑最接近那個數量的一列價格。
- **⑤ 生成品質把關**：回答用低隨機度（temperature 壓在 0.35，讓模型少自由發揮）壓住亂編；答得太短或只有半句話會被判為不合格、自動重答一次。

### 技術重點（真正做出來的東西）

- **RAG 檢索增強生成當底層架構**：不是讓大模型憑訓練記憶回答，而是每次都先從公司真實的商品/牌價/FAQ 資料中檢索出證據、再交給模型據此生成。模型回覆的每個商品、每個價格都有對應的真實資料列，不是模型「想像」出來的。
- **多層檢索：能精準查到就絕不動用語意搜尋**。這是刻意的設計原則，理由有二：一是省成本（把文字轉向量、查向量庫都要花錢與時間），二是保準確（客人已經給了明確料號時，語意搜尋反而可能抓到「意思相近但其實是別的商品」）。所以四層本地精準查排在前面，語意搜尋只當最後手段。
- **料號精準查走本地字典比對、不打網路**：用正則抓出客人訊息裡的料號（如 `33AA-0001`），到記憶體裡的「料號索引」做字典精準比對，命中就是確定命中（信心分數直接給滿分 1.0，而非相似度估算），不需要把文字轉向量、不需要連外，這就是毫秒級路徑的來源。
- **中文別名對照解決「客人不講料號、只講品類」**：客人說「有沒有帆布袋」「要鑰匙圈」時，系統靠一張人工維護的中文別名對照表把品類詞對到內部分類代碼（鑰匙圈→60DA、帆布袋→56CA、貼紙→33AA…），再走本地分類索引查，同樣不必動用語意搜尋。
- **語意搜尋當最後手段**：前四層全查不到，才把問題交給語意向量模型轉成「代表意思的向量」，拿去向量庫做相似度搜尋（用 Cosine 餘弦相似度，比較兩段文字的「意思夾角」有多接近）找最相近的商品。這條路徑要連外、要等大模型，是秒級（2–5 秒）路徑，所以被排到最後。
- **相似度不夠寧可不回**：語意搜尋設了相似度下限（門檻 0.2），找到的商品若相似度低於門檻就整批捨棄，寧可不回也不硬湊一個相近品塞給客人。
- **本地索引開機就備好**：料號索引、分類索引、中文詞掃描表三張表在服務啟動時就一次載入記憶體，之後查詢幾乎不用再讀檔；並用檔案的修改時間與大小判斷資料有沒有變、決定要不要重建索引，避免每次提問都重讀上萬筆資料。
- **一個入口吃多種問法、又不犧牲報價準確度**：客人一句話同時「找產品又問價」時，只要句子裡出現料號，就優先走料號精準查、完全跳過語意搜尋，用架構保住報價的準確度，避免語意搜尋把料號對應的商品抓錯。
- **增量更新（只重算變動那幾筆）**：商品或價格在來源試算表有異動時，系統比對本地紀錄，只對「新增／修改」的那幾列重新轉向量、只刪掉「來源已消失」的資料點，不整批砍掉重建——同步又快又省，也避免重建期間的服務空窗。每次同步還輸出一份報表（總筆數／變動／新增／更新／刪除）方便追蹤。
- **可觀測性：每一步都計時**：後端記錄每個環節花多少毫秒（排隊、解析、載入歷史、分類、料號查、分類查、中文詞查、轉向量、各次向量查詢、組 prompt、大模型生成、存檔、通知），前端逐段顯示，卡在哪一層一眼看得出來，方便定位效能瓶頸。
- **測試環境與正式共用同一套邏輯**：附一個瀏覽器測試介面，刻意共用與正式線上完全相同的分類／檢索／生成／對話記憶邏輯，讓測試結果貼近真實行為，而不是另寫一套「測試版」自欺欺人。

### 核心設計決策：把「不准亂報價」做進系統結構（三層堵死）

報價錯一次就是商業事故（自動化會放大錯誤，AI 篤定的語氣還會騙過客戶），所以這條不是靠一句話提醒 AI「不要亂講」，而是從三個層次讓 AI 手上**根本沒有可以亂猜的數字**：

- **第一層｜商品和價格分開存，只能用料號精準對應**：商品資料與牌價資料是兩份獨立的資料集（兩個獨立的向量庫 collection），彼此只能靠料號做精準對應（等於資料庫的精準 JOIN，只認完全相同的料號才配對得起來）。結構上就拿不到「相近商品的價格」——想借別的商品的價，連借的路都不存在。
- **第二層｜挑價格只在同一個料號的數量級距裡挑**：客人給了數量要報價時，系統只在「同一個料號」底下的多個數量級距中挑最接近的那一列，絕不跨料號去借別的商品的價。
- **第三層｜查不到就清空欄位、塞固定拒絕語**：如果這個料號真的沒有對應牌價，系統會直接把價格欄位清空、填上固定的一句「目前沒有此產品編號的精準牌價，需人工確認後報價」。等資料交到大模型生成回覆這一步時，它拿到的資料裡**根本沒有數字可以編**——拒絕不是靠模型自律，是資料層就沒給它機會。

另外還有兩種「拒絕」情境：商品存在但查不到該料號的價，回覆裡就把這個品項的價格位置顯示成「需人工確認後報價」（同一則回覆裡，有價的品項照常顯示價格、沒價的顯示這句，並列呈現）；商品本身查得不夠可靠時，不硬配對，改回「目前沒有足夠可靠的商品結果可直接推薦」，反問客人材質、尺寸、料號來縮小範圍。

### PM 力展現

- **先定義系統何時該閉嘴**：把「AI 主動說查不到」當成第一個要設計的功能，而不是事後補丁——先想清楚系統在什麼情況下該拒答，再談怎麼答得好。
- **按風險排序，不只追效率**：判斷「報錯價」比「查得慢」嚴重得多，因為自動化會放大錯誤、AI 篤定的語氣又會騙過客戶，所以優先堵死報錯價的風險，效率其次。
- **用架構逼出正確，不靠模型自律**：把「不准亂報價」落實成資料結構（價格獨立存放）與檢索規則（只認同料號精準對應），遠比寫一句話提醒 AI 可靠——提醒會被無視，結構不會。
- **把成本當產品變數**：透過 RAG 上的冷熱分層與多層檢索，讓多數查詢不動用較貴的語意搜尋與大模型，把算力花在真正需要語意判斷的模糊問法上。
- **一個 bot 服務多種需求**：靠「先分類＋冷熱分層＋多層檢索」，讓找產品、問規格、要報價、一般問答各自走最短路徑，而不是所有問題都丟給大模型硬解。
- **知識庫可持續維護**：中文別名對照、常見問答、分類對應都做成非工程人員也能擴充的獨立檔案，客戶的簡稱、口語、錯別字可以持續補進去。
- **誠實標注數字**：效能數字明白標「自測值、尚無正式量測」，不把估計當實測數據裸奔——可審查優先於好看。
- **限制講在明處**：問題分類目前是關鍵詞規則、不是 AI 意圖判斷，太口語的長尾問法可能分錯類；轉人工目前做到「明說要人工確認、系統把不確定案件導向人工」，是否有程式自動指派真人客服待確認，不誇大。
