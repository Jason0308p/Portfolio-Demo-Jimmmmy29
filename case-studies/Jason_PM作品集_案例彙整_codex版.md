## 工作方法

1. **先定義決策問題與資料邊界**：不把「人工慢」直接當需求，而是找出品質、一致性、風險或決策缺口。
2. **把高風險動作設計為可驗證流程**：預覽／試跑 → 人工確認 → 正式執行 → 讀回或抽樣驗證；不只相信 API 回傳成功。
3. **以資料與架構限制錯誤**：在價格、發布、追蹤設定等高風險場景，不靠提示詞要求 AI 小心，而是限制它可取得的資料與可執行的權限。
4. **把一次性工作變成可維護資產**：規則文件、欄位對照、批次日誌、斷點續跑、SOP 與健檢工具都納入交付物。

## 技術策略原則

- **精準路徑優先，模型路徑兜底**：能用結構化資料、規則或索引處理的問題，不先交給模型；模型只負責需要語意判斷的長尾情境。這同時降低成本、延遲與錯誤可見度。
- **將高風險流程做成「有證據的狀態轉換」**：商品下架、資料寫回、追蹤設定發布等動作，必須能指出前態、預計變更、執行結果與驗證結果；API 回覆成功不是唯一完成條件。
- **先設計失敗模式，再談功能**：外部來源會失效、平台欄位可能靜默寫入失敗、模型可能答錯、權限可能過期；系統設計需有冷卻、隔離、讀回、拒答與人工接手路徑。

## 01｜J1 商品文案自動化

**問題**：新品上架文案依賴人工撰寫，命名不一致、SEO 規則分散，且批次寫回內部系統時有靜默失敗風險。

**解法與架構**

```text
商品資料／商品圖 → 規則 Skill + Claude 生成／讀圖 → 預覽報表 →
欄位驗證 → 差異寫入 YiDa → 寫後讀回驗證 → 日誌／統計／主管摘要
```

- 以 Node.js 串接釘釘宜搭；將命名公式、SEO 關鍵字策略、硬性限制與自檢清單抽成單一規則模組，讓規則調整不必改動批次寫入核心。
- 資料稀缺的工單商品走圖片辨識分支；圖片與原始資料不足時留空，不由模型補造事實。
- 寫入引擎採 **diff update**，只更新變動欄位；預設 dry-run，確認後才實寫。
- 因應平台對失效欄位「回成功但不寫入」的特性，加入寫前欄位檢查與寫後讀回比對，將 API 成功改為資料一致才算成功。

**成果與可說明決策**

- 第一代批次引擎已投入實務資料同步；第二代 AI 生成仍為預覽型原型，兩者的成熟度與成效不混報。重點放在可預覽、差異寫入與寫後讀回驗證，而非單一批次處理量。
- 從供應端規格堆疊改為「使用情境／問題」前置命名；禁止無差異化的通用行銷詞塞入商品名。
- 曾引入單一品類關鍵字庫，評估維護成本後移除，改以原始商品資料推斷關鍵字：以跨品類可維護性取代短期特化。

**規則與資料品質治理**

- 篩選條件曾從容易變動的「商品狀態」收斂為「已取號未上架」：先釐清欄位的業務語意，避免把生命週期欄位誤當成待處理佇列而漏單。
- 商品名稱遵守單一主品類詞、材質統一寫法、單一容量值與賣點前置等規範；目的不只是文案好看，也降低近義詞堆疊、誤導性宣稱與搜尋噪音。
- 維護 HTML 上架版與純文字閱讀版兩種輸出，但內容同源、僅呈現格式不同，避免雙版本文案長期分歧。
- 每批輸出日誌、累積統計與管理摘要；失敗須附原因，不允許靜默略過，讓單筆商品可回查來源、生成結果與寫入紀錄。

**可延伸的面試敘事**：這不是「用 AI 寫商品文案」，而是把內容規則、資料品質檢查與安全寫回做成一條可持續改善的內容供應鏈。真正的風險在錯誤寫入與規則漂移，而不是模型能不能產生一段文字。

**PM 角色具體展現**：我先把問題定義為內容品質與可控性，而非單純加速打字；接著把命名規則、審核節點與追溯責任做成流程。當單一品類字庫與通用品類架構衝突時，選擇後者，並能說清楚短期品質與長期維護成本的取捨。

**策略發想與技術深度**：將「AI 生成」拆成可替換的能力層，而非把規則寫死在 prompt 裡。規則層負責一致性與合規，生成層負責將已知資料組織成文字，寫入層負責資料一致性；未來更換模型、增加品類或調整欄位時，不必重寫整條流程。這是以模組邊界控制 AI 不確定性的設計。

**面試重點**：展示的是「內容自動化 + 資料治理」；最關鍵的不是生成文案，而是如何避免錯寫、過度覆蓋與不可追溯。

## 02｜營運流程自動化

**問題**：傳產轉電商期間，社群、貨運與月結分散於人腦、Excel 與跨部門手動交接。

**方案**

- **社群數據同步**：用 n8n 驗證流程，再以 Python 實作可搬移版本；將 FB／IG／Threads 的異質欄位正規化，並以貼文唯一識別做 upsert（存在則更新、不存在才新增），避免重複列與歷史數據失真。
- **貨運 QR Code 流程**：從收貨到出貨串接四個斷點，讓倉儲與業務使用同一貨況資訊；以可掃描原型先取得倉庫採用，再推進至業務端。
- **財務月結**：針對跨表比對、規則固定且錯誤代價高的環節規劃自動化。

**技術與產品判斷**

- 將視覺流程工具用於跨服務編排與快速驗證；將需要版本控管、測試、排程部署與跨機器遷移的核心規則落在 Python。
- 移除未實際寫回的舊平台分支；網路失敗採重試，正式排程交由作業系統而非長駐程式自行迴圈。
- 用「重複性 × 規則明確 × 出錯代價」排優先序，不以主管提出的順序照單全收。

**證據邊界**：社群同步有完整可展示程式碼；貨運／財務的省時數字尚未完成前後量測，因此不列為已驗證 KPI。

**營運落地與取捨**

- 社群平台資料可取得程度受帳號權限與平台 API 限制影響；流程設計會將可穩定取得的欄位與尚不可用欄位分開處理，不把空白誤解為零成效。
- 貨運案以倉儲與業務的共同痛點切入：倉儲需要知道貨在哪一站、業務需要即時回應客戶。先讓實際使用者掃得到、看得到，再討論制度化，而非先要求全員改流程。
- Python 版本避免依賴過多外部套件，目標是能整包遷移到另一台電腦；連線失敗有重試與失敗紀錄，正式執行交給系統排程管理。
- 現階段最需要補的不是功能，而是量測設計：定義每條流程的基準工時、錯誤類型、處理量與採用率，才能把「有感變快」轉成可比較 KPI。

**可延伸的面試敘事**：我做的不是一次性腳本，而是先用流程工具降低驗證成本、再把成熟規則工程化，並把組織採用與可量測性納入產品範圍。

**PM 角色具體展現**：面對有限人力與大量需求，我提出排序框架而非被動接單；貨運案則先用低成本原型取得一線使用者回饋，讓跨部門推行從「要求配合」轉為「解決共同問題」。尚未量測的數字明確標記，下一步會把基準值與成效指標納入 rollout 設計。

**策略發想與技術深度**：社群同步的關鍵不是「把資料搬過去」，而是建立可重複執行的 idempotent 流程：同一貼文重跑多次，最終資料狀態仍一致。以貼文 ID 做 upsert、保留失敗紀錄、將欄位映射集中管理，才能在排程重試、平台延遲或後續加新渠道時避免資料膨脹。

## 03｜Shopify 電商營運整合

**問題**：正式店商品規模大、資料與內容分散；法規下架要同時變更 Shopify 與公司內部系統，手動作業慢且難稽核。

**架構與實作**

```text
Shopify Admin／Theme／Search
        ↕
React Router v7 + Prisma + Polaris 店內 App
        ↕
YiDa 內部表單 + Python 批次工具 + 進度檔／驗證日誌
```

- 維運範圍涵蓋商品、標籤、metafields、集合、封面、篩選器、內容／部落格、SEO、佈景主題、上下架、圖片與內部系統同步等 16 個面向。
- 自建店內 App 將跨三系統的下架動作封裝成一次操作；Python 批次工具支援並行處理、進度持久化與斷點續跑，並以試跑、人工確認與抽樣讀回驗證降低正式店操作風險。
- 以讀取現況、最小變更、備份、試跑、人審、正式執行與線上驗證作為正式店變更的標準流程。
- 對中文搜尋從「擴大比對」翻轉為「精準收斂」：限定標題比對、前端商品卡評分重排與同義詞治理。

**已驗證成果**

- 正式店 **14,317** 件商品；**360/360** 個集合有封面圖。
- 合規下架 **148 件／約 3.4 分鐘／0 錯**；單筆約 14.4 秒降至約 1.4 秒，約 **10 倍**改善。
- 同一關鍵字搜尋結果 **359 → 232（-35%）**，對應使用者要「更準、更精簡」的需求。
- 建立 **227 組／1,387 詞**中文同義詞字庫與 12 篇產業採購指南；沉澱 7 套自建工具、101 筆工作日誌。

**面試重點**：清楚區分測試店的大量驗證與正式店成績；能說明 build-vs-buy、跨系統一致性與高風險上線治理。

**更完整的營運與工程細節**

- **商品資料與搜尋**：建立 6 個商品 metafields，承接徽章、短說明、賣點、分類與搜尋加權資訊；同義詞字庫由商品資料與核心編碼萃取，再回填搜尋治理流程。
- **集合與內容架構**：依標籤／類型讓商品進入對應集合；產業案例頁改為 12 個產業、每組 3 張卡片的互動式呈現，並建立可重複使用的內容區塊，降低後續改版成本。
- **SEO 與健檢**：修正分享縮圖、主標題、頁面描述與結構化標記；另建唯讀健檢工具掃描缺漏並以抽樣核對商品資料，讓每月檢查有一致基準。
- **不可逆動作的保護**：每次佈景或頁面調整前備份；法規下架先以試跑產生確認清單，再正式執行，最後檢查 Shopify 與 YiDa 的狀態是否一致。
- **事故復盤**：文章遷移曾因更新覆蓋原文，之後將規則改為「遷移／複製一律新建、不覆蓋」，並以 19 篇複製重建驗證新流程。這個經驗後續也延伸為寫前讀取、寫後驗證與線上驗證。
- **系統邊界判斷**：確認某些 Shopify 欄位缺乏可安全操作的介面後，未以高風險全站覆蓋強行自動化，而是交付正確文案與明確的人工步驟。

**為什麼自建而非採購**：先檢視既有工具，核心缺口是無法同步公司內部 YiDa 表單；因此自建的價值不在重做 Shopify，而在將「正式店狀態 + 內部合規紀錄」收斂為一次可稽核的原子操作。

**PM 角色具體展現**：此案不只是在改網站，而是在管理正式營運的變更風險。我劃分測試店與正式店的證據範圍、為高風險動作建立發布門檻、把事故轉成 SOP，並在平台能力不足時主動調整交付方式，而非為了「全自動」犧牲正確性。

**策略發想與技術深度**：將「下架」視為跨系統交易，而非單一 Shopify 操作。雖無法假設三個外部系統提供真正的資料庫 transaction，仍可透過進度檔、逐系統結果、可重跑步驟與抽樣讀回，建立近似 saga 的補償／復原能力；這比單純批次呼叫 API 更接近正式營運所需的可稽核性。

## 04｜GA4 + GSC + GTM 跨源數據儀表板

**問題**：網站行為、搜尋成效與追蹤設定分散在不同後台；主管需要可解讀的洞察，工程／行銷需要可控的追蹤配置。

**架構**

```text
GA4 Data API + GSC API + GTM API v2
             ↓（統一期間與指標口徑）
Python FastMCP／資料擷取與產表程式
             ↓
Plotly + HTML/JS 雙語互動報表 + AI 洞察分頁
```

- 以 32 個事件回答具體決策：將詢價送出定義為獨立轉換；LINE 點擊依 5 個版位帶上位置資訊；站內搜尋、內容深度與流量來源均可回溯。
- 自建 13 個工具動作，讓 AI 可讀寫 GTM 草稿設定；改前先讀完整設定、修改後再整包回寫，避免覆蓋未改欄位。
- AI 僅能編輯草稿，沒有發布權；最終 publish 由人工核對，確保自動化不越過治理邊界。
- 報表由同一產表程式生成中英雙語與多時間窗版本，禁止手改產物，避免重跑覆蓋與版本漂移。

**已驗證成果**

- 近 180 天：網站約 **82 萬**瀏覽、**750** 次詢價送出；正式收集 **32** 個事件。
- 正式 GTM 設定：**17 tags／16 triggers／9 variables**。
- 線上 demo 使用去識別示意資料、AI 分析頁為前端模擬，已與真實資料儀表板清楚切分。

**資料、報表與治理細節**

- 每個來源各自先擷取原始資料，再對齊日期區間、時區與統計口徑；避免 GA4 的行為數據、GSC 的搜尋數據與 GTM 設定在同一張圖表中被錯誤直接比較。
- 報表涵蓋整體摘要、SEO 機會、轉換漏斗與 AI 引薦四類問題；其中搜尋圖以曝光、點擊、排名三軸呈現，並刻意反轉排名軸，讓「線向上」即代表排名改善。
- 以星期 × 時段熱力圖協助判斷內容／投放時段；以進站頁分布與標色辨識可疑機器人流量，不將異常流量包裝為成效。
- GA4 與 GTM 操作使用不同授權設定，避免一種授權刷新後使另一種失效；資料讀取與設定修改亦分開管理，降低權限耦合。
- 先建立 page type、interaction type 與 campaign source 命名規範，再擴充事件，確保日後可以分群、歸因與比較，不會堆出無法解讀的事件名稱。

**可延伸的面試敘事**：儀表板的交付不是「幾張漂亮圖」，而是一套從商業問題、埋點命名、資料口徑、權限治理到可解讀洞察的 measurement product。

**PM 角色具體展現**：先和需求方對齊「要做什麼決策」，才定義事件與圖表，而非先蒐集所有可得數據。將管理者需要的雙語洞察、行銷需要的轉換判讀、工程需要的 GTM 治理整合成同一產品；對 AI 設定編輯保留人工發布權，是在效率與責任歸屬之間做明確切分。

**策略發想與技術深度**：把追蹤規格當成產品契約，而非埋碼清單。事件名稱、參數、頁面類型與來源命名規範先固定，才能讓儀表板、投放優化與未來分析共用同一語言。FastMCP 工具則把 GTM 的讀取、草稿修改與發布責任拆開，讓 AI 提升設定效率，但不取得不可逆的生產發布權。

## 05｜台股輿情分析系統

**問題**：需要持續整合社群、新聞與影音討論，將噪音轉成可追蹤的個股／族群情緒，同時控制 AI 成本與來源失效風險。

**架構**

```text
20+ 資料來源 → 容錯蒐集／去重 → 規則情緒初判 →
必要時 Claude Haiku 語意判定 → SQLite 工作資料／Cloudflare D1 即時查詢 →
Cloudflare Workers API + Dashboard（Gmail Email OTP）／Telegram／Email
```

- **YouTube 影音雙路徑**：有現成字幕時優先透過字幕 API 取得逐字稿；無字幕影片或直播回放則以 `yt-dlp` 擷取音訊，依時長切分成可重試的片段後，交由 **faster-whisper** 語音辨識轉寫，再彙整為個股分析文本。字幕擷取另設計多客戶端相容性與來源降級策略；遇到限制時不無限重試，改記錄、降頻或停用來源。
- **動態社群來源**：Threads、CMoney 等動態頁以 Playwright 瀏覽器自動化取得；在具授權的帳號情境下使用登入 session 讀取動態內容，並將憑證失效視為可預期故障，隔離單一來源而不阻斷全批任務。
- **鉅亨網 connector（已啟用）**：逆向分析公開 Web Client 的資料請求流程，定位其內部 REST API 與必要的 request context（如 Referer）；將回應轉換為統一的新聞／輿情資料格式後納入主管線。此作法的價值在於，面對未提供適用正式 API 的資料來源，仍能以可維護的 connector 取得結構化資料，而非依賴脆弱的頁面文字擷取。
- **來源容錯**：不同來源依特性採不同擷取器；來源被封鎖、格式變更或憑證過期時，記錄失敗原因、進入冷卻或隔離，主流程仍完成其餘資料蒐集。
- 先用本地規則處理明確情緒，重大事件或不確定內容才送 AI；以低成本模型、批次與減少固定開銷控制成本。
- 報告從多次 DB 查詢改為一次取數、記憶體運算，產出由數秒降至 **0.01 秒**。
- **Cloudflare Workers + 自建 Gmail Email OTP 驗證**：Workers 提供登入、報告與 D1 即時查詢 API；白名單信箱由 Gmail 寄送一次性驗證碼，驗證碼與登入流程狀態存於 Cloudflare KV，登入 session 以 HMAC 簽名驗證完整性。安全設計重點為 OTP 寄送／驗證嘗試限流、短效單次使用碼、HttpOnly／Secure／SameSite session cookie，以及以 CSP 降低前端注入風險。

**已驗證成果**

- 自 2026-05-21 連續運作約 2 個月；**42** 份日報、**35,597** 則貼文、**36,760** 筆情緒評分，追蹤 **61** 支股票／**26** 個族群。
- 規則層實測減少約 **17%** AI 呼叫（非初期估計的 60–80%）；固定呼叫開銷降低約 **80%**。
- 未做人工標註集驗證，因此不宣稱情緒準確率。

**資料管線與成本設計細節**

- 主流程支援完整執行、社群即時、新聞、YouTube 與僅重出報告等模式；同時搭配排程與來源冷卻機制，避免短時間重複抓取與不必要的 API／爬取成本。
- 情緒判定不只依正負面詞，而是將重大事件（如財報、漲停、升息）列為必須交 AI 複判的訊號；以較高成本換取高影響訊息的召回率。
- 模型選擇、批次大小與每次呼叫附帶內容都經過調整；成本優化結論來自兩個月實際記錄，而非只依初期預估。
- SQLite 作為本地工作與歷史資料層，Cloudflare **D1** 提供 Dashboard 即時查詢 API；每日產物再同步至網站、Telegram 與 Email，將分析、查詢、留存與通知拆開，避免單一輸出渠道失效。
- 報告與 API 透過自動部署上線到 Cloudflare Workers，將本地排程產出的資料與對外可查詢服務分離；前者重視批次穩定性，後者重視讀取延遲與可用性。
- 對被阻擋的來源採停損與降頻，不以無限重試硬撞；把外部網站變動視為常態故障，而非例外。

**可延伸的面試敘事**：這個案子的亮點是端到端 production ownership，以及用實際執行資料推翻「規則可省 60–80% AI」的初版假設後，仍能重新定位真正的成本槓桿。

**PM 角色具體展現**：先將「情緒分析準不準」拆成資料覆蓋、處理成本、訊號優先級與發布可靠性四個可管理問題。當實測推翻原本的節省假設，不用原先漂亮的估算硬撐，而是回到執行紀錄找可改善的模型、批次與呼叫成本；這是以證據調整策略，而非只優化既有方案。

**策略發想與技術深度**：蒐集層採「可替換 connector + 共同失敗處理」而非為每個網站寫一條不可維護的專案流程；分析層則採規則分流與模型複判。兩者共同的策略是：把最常變、最不可靠、最昂貴的環節隔離，讓新來源、模型替換或單一來源失效不需重構整個產品。

## 06｜LINE RAG 智能報價客服

**問題**：客服同時要找商品、回答規格與報價；速度重要，但錯報價格是商業事故，不能只依賴 LLM 自我約束。

**架構**

```text
LINE 訊息 → 規則分類 → 精準檢索階梯（料號／分類／別名／關鍵字）
        → 必要時 Embedding + Qdrant 語意搜尋 → 回答品質檢查 → LINE 回覆／轉人工

商品資料 ──以料號精準關聯── 價格級距資料
```

- 服務啟動即把料號、分類與別名索引載入記憶體；常見查詢依序走料號、分類、別名與關鍵字等精準路徑，只有無法可靠命中的模糊問法才產生 Gemini embedding、查詢 Qdrant。
- 價格只可在「相同料號」的數量級距內選取；沒有精準價格即清空價格欄位、明示需人工確認，模型無法取得可臆測的相近商品價格。
- 語意結果低於相似度門檻即拒答並追問料號、材質或尺寸；商品／價格變動採增量更新，不因少量異動重建全量向量與索引。
- 記錄分類、檢索、生成各階段延遲，能定位效能瓶頸。

**成果與邊界**

- 已索引 **16,084** 件商品、**5,319** 個價格層、**65** 則 FAQ。
- 料號精準查為毫秒級，相較語意搜尋約 2–5 秒；AI 成本節省約 60%、業務回覆 10 分鐘降至 2 分鐘為自測，尚非正式量測。

**檢索、報價與可維護性細節**

- 入口先以規則區分找產品、一般問答與混合問題；混合問題只要帶料號，就優先保住精準商品查詢，再處理價格或說明，避免模糊語意搜尋干擾報價。
- 產品檢索有明確階梯：料號 → 分類代碼 → 中文別名 → 關鍵字 → 語意搜尋。每一層命中即停止，目標是將查詢導向成本最低、可解釋性最高的路徑。
- 料號比較前統一大小寫與格式；回覆生成採低隨機度，內容過短或不完整會自動重試，降低客服訊息不完整的機率。
- 商品資料、價格級距、中文別名與 FAQ 分開維護；非工程人員可以持續補充客戶口語、縮寫與錯別字，不必每次調整都修改核心程式。
- 後端記錄分類、料號查詢、分類查詢、向量搜尋與生成的逐段耗時，讓效能優化有可觀測資料，而不是憑感覺調整。

**可延伸的面試敘事**：RAG 的重點不是「能回答」，而是能辨識何時必須拒答。這裡把拒答條件、價格資料隔離與同料號限制設計在資料與檢索層，而非交給模型遵守提示詞。

**PM 角色具體展現**：先與業務風險對齊優先序：錯報價的損失遠大於回覆慢，因此把「拒答與轉人工」視為核心功能而非例外。再把客服、業務與維護者的需求分層：客戶獲得明確下一步、業務只處理高價值例外、非工程人員能持續補充知識庫。

**策略發想與技術深度**：檢索階梯本質上是「風險與成本由低到高」的決策樹：料號精確命中可直接回答；類別與別名仍具可解釋性；向量檢索只負責找候選而非決定價格；相似度不足即中止。這比所有問題直接丟進 RAG 更可控，也能針對每一層量測命中率、延遲與人工轉接率。

## 可延伸追問：我會怎麼回答

- **為什麼不用 AI 處理全部？** AI 是成本、延遲與不可預期來源；先用精準規則與索引處理確定性問題，把模型留給語意判斷。
- **如何避免自動化造成更大事故？** 讓高風險動作可預覽、可回滾、有人審；寫入後以資料讀回或抽樣驗證，而不是只看 HTTP 200。
- **如何面對數字不完整？** 已驗證數據、測試店數據、示意資料與自測值分開標示；未量測的準確率、節省工時或 ROI 不會包裝成成果。
- **你的 PM 價值是什麼？** 把技術選擇接回業務問題、風險與維運成本：知道該自建、該買現成，也知道何時應降級成人工步驟而非硬做高風險自動化。
- **遇到沒有適用官方 API 的來源怎麼處理？** 以鉅亨網為例，我先分析公開 Web Client 的資料請求流程，辨識取得內容所需的內部資料介面與請求上下文，再將回應統一轉為結構化 JSON connector。相較於直接解析 HTML，這種方式欄位更明確、資料清洗更少，也較容易監控接口或格式變更；若來源限制改變，connector 會被隔離、降頻或停用，不影響整體報告產出。
