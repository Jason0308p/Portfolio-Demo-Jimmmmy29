### 面試時要主動處理的疑慮

- **「你偏工程，真的像 PM 嗎？」** 回答重點不是列技術，而是每案先講：誰的什麼決策被改善、你如何排序、為何採此方案、如何驗證採用與風險。
- **「你是一人完成，怎麼證明能與團隊合作？」** 以貨運案的倉儲／業務採用、GA4 的管理者／行銷／工程多角色需求、Shopify 正式店變更的人工審核機制，說明你知道角色分工與責任邊界。
- **「數字是否可信？」** 主動區分已驗證數據、自測值、待驗證 KPI；這不是弱點，而是產品決策與數據治理的基本紀律。
- **「AI 產品和一般聊天機器人有何不同？」** 用 RAG 的拒答／價格隔離、台股的成本分流、GTM 的草稿權限回答：核心是可靠性、治理與商業風險，不是模型串接本身。

## 精選專案經歷

### 1. Shopify 電商營運整合｜Technical PM／產品營運

**情境**：負責正式 Shopify 店的技術營運；商品規模大，且法規下架需同步 Shopify、內部表單與紀錄，手動操作耗時、難稽核。

**我做了什麼**

- 規劃並執行商品、metafields、集合、篩選器、內容頁、SEO、主題、圖片、上下架與內部系統同步等 16 個營運面向。
- 自建 React Router v7 + Prisma + Polaris 店內 App 與 Python 批次工具，將跨三系統下架收斂為單次可追蹤操作；支援試跑、並行處理、進度持久化、斷點續跑與抽樣讀回驗證。
- 將正式站變更固化為「讀取現況 → 最小變更 → 備份 → 試跑 → 人工確認 → 執行 → 線上驗證」流程；把一次文章覆蓋事故轉為「遷移一律新建」的 SOP。
- 重新定義中文搜尋目標：從擴大召回改為精準收斂，建立同義詞治理與前端評分重排。

**成果**

- 正式店 **14,317** 件商品；**360/360** 個集合完成封面圖覆蓋。
- 合規下架 **148 件、約 3.4 分鐘、0 錯**；單筆處理約由 14.4 秒降至約 1.4 秒，約 **10 倍**改善。
- 同一關鍵字的搜尋結果 **359 → 232（-35%）**；建立 **227 組／1,387 詞**中文同義詞字庫與 12 篇產業採購指南。

**展現的 PM 價值**：先確認現成工具無法同步公司內部資料才自建；區分測試店與正式店證據；在平台能力有限時保留人工步驟，不以高風險自動化換取表面上的完整度。

### 2. GA4 + GSC + GTM 跨源數據儀表板｜MarTech／Growth PM

**情境**：網站行為、搜尋成效與追蹤設定分散於三個後台，缺乏統一口徑與能直接支持決策的報表。

**我做了什麼**

- 以商業問題回推追蹤規格，建立 **32 個**事件：詢價送出獨立為核心轉換，LINE 點擊拆為 5 個版位，並追蹤站內搜尋、內容深度與 AI 引薦流量。
- 串接 GA4 Data API、GSC API、GTM API v2，以 Python FastMCP 建立 **13 個**可讀寫 GTM 草稿的工具動作；AI 只能改草稿，正式發布保留人工核對。
- 對齊各來源的日期、時區與指標口徑，以 Plotly + HTML/JS 產出中英雙語、多時間窗互動報表；將產物視為編譯結果，禁止手動直接修改。
- 建立事件／參數／來源命名規範，讓追蹤設定、報表與後續分析共享資料契約。

**成果**

- 近 180 天約 **82 萬**瀏覽、**750** 次詢價送出。
- 正式 GTM 設定為 **17 tags／16 triggers／9 variables**；正式收集 **32** 個使用者行為事件。

**展現的 PM 價值**：將主管洞察、行銷優化與工程治理整合成同一 measurement product；明確標示示意 demo、待核算成效與真實資料的差異，避免數據被誤用。

### 3. 台股輿情分析系統｜AI Product Manager／Technical PM

**情境**：需要把新聞、社群與影音討論持續轉化為可追蹤的個股／族群情緒，同時面對資料來源不穩定、影音無字幕與 AI 成本問題。

**我做了什麼**

- 設計多來源 connector 架構：新聞、社群、YouTube 等來源個別擷取，失效時隔離、冷卻或停用，不阻斷整體日報。
- YouTube 優先以字幕 API 取得逐字稿；無字幕影片或直播回放則用 `yt-dlp` 擷取音訊、切段，以 **faster-whisper** 轉寫後彙整分析。
- 以規則初判＋ Claude Haiku 語意複判的兩層架構處理情緒；重大事件優先送模型，並從模型、批次與呼叫內容三層控制成本。
- 以 Cloudflare Workers 提供 Dashboard／登入／D1 查詢 API；以 Gmail Email OTP、KV 與 HMAC 簽名 session 保護白名單內容；自動部署報告與 API。
- 以鉅亨網為例，分析公開 Web Client 的資料請求流程，整合結構化 REST 資料到統一 connector，降低 HTML 解析與頁面改版風險。

**成果**

- 2026-05-21 起連續運作約 2 個月；產出 **42** 份日報、處理 **35,597** 則貼文與 **36,760** 筆情緒評分，追蹤 **61** 支股票／**26** 個族群。
- 報告產出由數秒降至 **0.01 秒**；規則層實測減少約 **17%** AI 呼叫，單次呼叫固定開銷降低約 **80%**。

**展現的 PM 價值**：以實際執行紀錄推翻早期「可省 60–80% AI 呼叫」假設，重新找出成本槓桿；不在未完成標註驗證的情況下宣稱情緒準確率。

### 4. LINE RAG 智能報價客服｜AI Product Manager

**情境**：全站商品與牌價資訊龐大；客服需要快速回覆，但錯報價格會直接形成商業與信任風險。

**我做了什麼**

- 將查詢設計為檢索階梯：料號 → 分類 → 中文別名 → 關鍵字 → Gemini embedding + Qdrant；命中即停止，只有模糊問法才進語意搜尋。
- 商品與價格資料分離，價格只能以「同一料號 × 數量級距」精準取得；沒有對應價格就清空數字並明示需人工確認，禁止跨商品借價。
- 為低相似度結果設拒答門檻，並請使用者補料號、尺寸或材質；商品與牌價異動走增量更新，避免全庫重建。
- 完整記錄分類、檢索與生成的逐段耗時，作為命中率、延遲與人工轉接率的後續優化基礎。

**成果與證據邊界**

- 已索引 **16,084** 件商品、**5,319** 個價格層與 **65** 則 FAQ。
- 料號精準查為毫秒級；AI 成本節省約 60%、業務回覆由 10 分鐘至 2 分鐘為自測值，尚未作正式量測。

**展現的 PM 價值**：將「拒答與轉人工」設計成核心功能，優先保護報價正確性；把客戶體驗、業務例外處理與知識庫維護拆成可治理的角色與流程。

### 5. 商品文案與營運流程自動化｜Product Operations／AI Automation

- 將商品命名、SEO 規則、欄位限制與自檢清單模組化，搭配 AI 生成與圖片辨識，並以預覽、差異寫入、寫前欄位檢查與寫後讀回保障內容同步品質。
- 將 FB／IG／Threads 社群數據正規化，以貼文 ID 做 idempotent upsert，避免排程重跑產生重複列；以 n8n 快速驗證流程，再將穩定規則工程化為 Python。
- 以「重複性 × 規則明確性 × 出錯代價」排序貨運、財務與社群自動化，並以一線原型促進跨部門採用。

**展現的 PM 價值**：從「替人加速」升級為「讓品質、規則與責任可被管理」；未完成前後量測的工時改善不包裝成已驗證 KPI。

## 投遞策略

- **AI PM 職缺**：優先放台股輿情與 LINE RAG；強調「成本、可靠性、拒答、人工接手」而非只列使用模型。
- **MarTech／Growth 職缺**：優先放 GA4/GTM；強調事件規格、轉換定義、資料口徑、洞察到決策的閉環。
- **電商／Product Ops 職缺**：優先放 Shopify；強調正式店規模、跨系統同步、合規風險與營運效率。
- **Technical PM 職缺**：四案皆可放，但每案濃縮成「問題 → 決策 → 架構 → 可驗證成果」四行，避免被誤認為純工程履歷。

## 面試自我介紹（60 秒版）

我是一位偏技術型的產品經理，工作重點是把營運或商業問題落成可維護的產品與流程。過去我一方面負責正式 Shopify 店的商品、搜尋、內容與法規下架整合；另一方面做 GA4／GTM 數據追蹤與報表產品，也實作 AI 輿情分析及 LINE RAG 報價客服。

我的方法不是只追求自動化，而是先釐清哪裡的錯誤代價最高，再設計可驗證的流程。例如商品批次寫入會預覽與讀回驗證，GTM 讓 AI 改草稿但不給發布權，RAG 沒有精準價格就拒答並轉人工。我希望在 AI PM、MarTech 或電商產品營運職位，繼續做能真正連接商業決策、系統能力與使用者採用的產品。
